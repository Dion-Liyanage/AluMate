================================================================================
  2. PROBLEM STATEMENT
================================================================================

  Many aluminium fabrication businesses struggle with:

  - Tracking and managing fabrication orders efficiently
  - Maintaining accurate inventory of raw materials and finished products
  - Communicating order progress and updates to customers
  - Scheduling and managing service/maintenance requests
  - Generating accurate quotations and invoices

  Current processes are manual, paper-based, fragmented, or use disconnected
  tools. AluMate replaces all of this with a single modern web platform.

================================================================================
  3. PROJECT OBJECTIVES
================================================================================

  1. Provide a centralized order and service management system
  2. Enable customers to request quotes, place orders, and track progress
  3. Support fabrication job scheduling and workflow management
  4. Improve communication between the business and its customers
  5. Provide administrators with tools for efficient business operations
  6. Ensure data security and role-based access control
  7. Design a scalable and maintainable system using modern technologies

================================================================================
  4. SYSTEM USERS & ROLES
================================================================================

  ROLE: customer
  ---------------
  - Can register and login
  - Can request quotations for aluminium fabrication work
  - Can place and manage fabrication orders
  - Can track order/fabrication progress in real-time
  - Can view service history and past orders
  - Can receive notifications and updates on order status
  - Can submit service/maintenance requests (repair, maintenance, installation)
  - Has a profile page with personal details

  ROLE: admin
  ---------------
  - Can login (admin accounts are pre-created or seeded)
  - Can manage ALL orders (view, update status, assign, complete)
  - Can create and manage quotations
  - Can handle service requests
  - Can manage customer accounts (view, update, deactivate)
  - Can track inventory (raw materials and finished products)
  - Can manage workforce and job scheduling
  - Can view business analytics and reports
  - Has full role-based access control

  There are ONLY two roles: "customer" and "admin". No other roles exist.

  10. DATABASE SCHEMA (MongoDB Collections)
================================================================================

  COLLECTION: users
  ------------------
  {
    _id:          ObjectId (auto),
    email:        String (unique, required, lowercase, trimmed),
    password:     String (required, hashed with bcrypt),
    firstName:    String (required, trimmed),
    lastName:     String (required, trimmed),
    phone:        String (optional),
    address:      String (optional),
    role:         String (enum: ['customer', 'admin'], default: 'customer'),
    isActive:     Boolean (default: true),
    createdAt:    Date (auto),
    updatedAt:    Date (auto)
  }
  Indexes: { email: 1 } (unique)

  COLLECTION: orders
  ------------------
  {
    _id:          ObjectId (auto),
    customerId:   ObjectId (ref: users, required),
    title:        String (required),
    description:  String (required),
    materialType: String (optional, e.g. "6063 Aluminium", "7075 Aluminium"),
    dimensions:   String (optional, e.g. "2400mm x 1200mm x 3mm"),
    quantity:     Number (optional),
    status:       String (enum: ['pending','quoted','confirmed','in-progress',
                  'completed','cancelled'], default: 'pending'),
    quotationId:  ObjectId (ref: quotations, optional),
    assignedTo:   String (optional, worker/team name),
    totalAmount:  Number (optional),
    notes:        [{ message: String, createdBy: String, createdAt: Date }],
    createdAt:    Date (auto),
    updatedAt:    Date (auto)
  }
  Indexes: { customerId: 1 }, { status: 1 }

  COLLECTION: quotations
  ----------------------
  {
    _id:          ObjectId (auto),
    customerId:   ObjectId (ref: users, required),
    orderId:      ObjectId (ref: orders, optional),
    items:        [{
                    description: String,
                    material:    String,
                    dimensions:  String,
                    quantity:    Number,
                    unitPrice:   Number,
                    totalPrice:  Number
                  }],
    totalAmount:  Number (required),
    status:       String (enum: ['draft','sent','accepted','rejected'],
                  default: 'draft'),
    validUntil:   Date (required),
    notes:        String (optional),
    createdAt:    Date (auto),
    updatedAt:    Date (auto)
  }
  Indexes: { customerId: 1 }, { orderId: 1 }

  COLLECTION: service_requests
  ----------------------------
  {
    _id:          ObjectId (auto),
    customerId:   ObjectId (ref: users, required),
    type:         String (enum: ['maintenance','repair','installation'], required),
    description:  String (required),
    status:       String (enum: ['pending','scheduled','in-progress','completed'],
                  default: 'pending'),
    scheduledDate: Date (optional),
    completedDate: Date (optional),
    assignedTo:   String (optional),
    notes:        String (optional),
    createdAt:    Date (auto),
    updatedAt:    Date (auto)
  }
  Indexes: { customerId: 1 }, { status: 1 }

  COLLECTION: inventory
  ---------------------
  {
    _id:          ObjectId (auto),
    name:         String (required),
    description:  String (optional),
    category:     String (enum: ['raw-material','finished-product'], required),
    quantity:     Number (required, default: 0),
    unit:         String (required, e.g. 'kg', 'sheets', 'meters', 'pieces'),
    unitPrice:    Number (optional),
    reorderLevel: Number (required, default: 0),
    supplier:     String (optional),
    location:     String (optional, e.g. 'Warehouse A'),
    createdAt:    Date (auto),
    updatedAt:    Date (auto)
  }
  Indexes: { category: 1 }, { name: 1 }

  COLLECTION: notifications
  -------------------------
  {
    _id:          ObjectId (auto),
    userId:       ObjectId (ref: users, required),
    title:        String (required),
    message:      String (required),
    type:         String (enum: ['order','quotation','service','system'],
                  required),
    isRead:       Boolean (default: false),
    linkTo:       String (optional, e.g. '/orders/abc123' for navigation),
    createdAt:    Date (auto)
  }
  Indexes: { userId: 1, isRead: 1 }, { createdAt: -1 }

================================================================================
  11. API ENDPOINTS (Backend REST API Design)
================================================================================

  Base URL: http://localhost:3001/api/v1
  All responses follow: { success: boolean, data?: any, message?: string }

  AUTHENTICATION:
  ---------------
  POST   /auth/register          — Register new customer
         Body: { firstName, lastName, email, phone?, password }
         Returns: { success, message }

  POST   /auth/login             — Login
         Body: { email, password }
         Returns: { success, data: { token, user } }

  GET    /auth/me                — Get current user (requires JWT)
         Returns: { success, data: { user } }

  POST   /auth/logout            — Logout (clear cookie if using cookies)

  ORDERS (Customer):
  ------------------
  GET    /orders                 — Get customer's orders (auth: customer)
         Query: ?status=pending&page=1&limit=10
  POST   /orders                 — Create new order (auth: customer)
  GET    /orders/:id             — Get order by ID (auth: customer, own only)
  PATCH  /orders/:id/cancel      — Cancel own order (auth: customer)

  ORDERS (Admin):
  ---------------
  GET    /admin/orders           — Get all orders (auth: admin)
         Query: ?status=&customerId=&page=1&limit=10&sort=-createdAt
  GET    /admin/orders/:id       — Get any order (auth: admin)
  PATCH  /admin/orders/:id       — Update order (status, notes, assignedTo)
  DELETE /admin/orders/:id       — Delete order (auth: admin)

  QUOTATIONS (Customer):
  ----------------------
  GET    /quotations             — Get customer's quotations (auth: customer)
  POST   /quotations/request     — Request a quotation (auth: customer)
  GET    /quotations/:id         — Get quotation by ID (auth: customer)
  PATCH  /quotations/:id/accept  — Accept quotation (auth: customer)
  PATCH  /quotations/:id/reject  — Reject quotation (auth: customer)

  QUOTATIONS (Admin):
  -------------------
  GET    /admin/quotations       — Get all quotations (auth: admin)
  POST   /admin/quotations       — Create quotation for customer (auth: admin)
  PATCH  /admin/quotations/:id   — Update quotation (auth: admin)
  DELETE /admin/quotations/:id   — Delete quotation (auth: admin)

  SERVICE REQUESTS (Customer):
  ----------------------------
  GET    /services               — Get customer's service requests
  POST   /services               — Create service request
  GET    /services/:id           — Get service request by ID

  SERVICE REQUESTS (Admin):
  -------------------------
  GET    /admin/services         — Get all service requests

================================================================================
  14. AUTHENTICATION & AUTHORIZATION
================================================================================

  FLOW:
  -----
  1. User enters email + password on login page
  2. Frontend sends POST /api/v1/auth/login
  3. Backend validates credentials, returns JWT token + user object
  4. Frontend stores token (localStorage or HTTP-only cookie)
  5. Frontend stores user in AuthContext
  6. All subsequent API calls include token in Authorization header:
     Authorization: Bearer <token>
  7. Backend verifies token on every protected route
  8. Backend checks role for admin-only routes

  JWT PAYLOAD:
  ------------
  {
    sub: userId (string),
    email: email (string),
    role: 'customer' | 'admin',
    iat: issued at timestamp,
    exp: expiration timestamp (e.g. 7 days)
  }

  NESTJS IMPLEMENTATION:
  ----------------------
  - AuthModule with AuthService, AuthController
  - JwtStrategy (passport-jwt) for token validation
  - LocalStrategy (passport-local) for login validation
  - JwtAuthGuard — apply to all protected routes
  - RolesGuard — check user role against @Roles() decorator
  - Example:
    @UseGuards(JwtAuthGuard, RolesGuard)
    @Roles('admin')
    @Get('admin/orders')
    getAllOrders() { ... }

  FRONTEND IMPLEMENTATION:
  ------------------------
  - AuthContext (React Context) providing:
    * user: User | null
    * token: string | null
    * isAuthenticated: boolean
    * isLoading: boolean
    * login(email, password): Promise
    * register(data): Promise
    * logout(): void
  - AuthProvider wrapping the app in layout.tsx
  - useAuth() hook to access context
  - ProtectedRoute component or middleware to check auth
  - Route-level protection using Next.js middleware (middleware.ts):
    * Check for token cookie/header
    * Redirect unauthenticated users to /login
    * Redirect unauthorized roles

  21. BUSINESS LOGIC & WORKFLOWS
================================================================================

  ORDER LIFECYCLE:
  ----------------
  1. Customer creates order (status: pending)
  2. Admin reviews order, creates quotation → (status: quoted)
  3. Customer receives quotation notification
  4. Customer accepts quotation → (status: confirmed)
     OR Customer rejects quotation → admin may re-quote
  5. Admin assigns order to workforce → (status: in-progress)
  6. Admin marks order complete → (status: completed)
  At any point before in-progress, customer can cancel → (status: cancelled)

  QUOTATION LIFECYCLE:
  --------------------
  1. Customer requests quotation (or admin creates one for an order)
  2. Admin creates quotation with line items (status: draft)
  3. Admin sends quotation to customer (status: sent)
  4. Customer accepts (status: accepted) → linked order moves to confirmed
     OR Customer rejects (status: rejected)

  SERVICE REQUEST LIFECYCLE:
  --------------------------
  1. Customer submits service request (status: pending)
  2. Admin reviews and schedules (status: scheduled, sets scheduledDate)
  3. Work begins (status: in-progress)
  4. Work completed (status: completed, sets completedDate)

  NOTIFICATION TRIGGERS:
  -----------------------
  - Order status changes → notify customer
  - New quotation sent → notify customer
  - Quotation accepted/rejected → notify admin
  - New order placed → notify admin
  - New service request → notify admin
  - Service request scheduled → notify customer
  - Low stock alert → notify admin
  - Announcements → notify targeted users

  INVENTORY RULES:
  ----------------
  - When quantity <= reorderLevel, item shows "Low Stock" warning
  - Admin can manually update quantities (stock in/out)
  - Ideally track stock transactions with timestamps (future enhancement)
